## 1. 为什么垃圾 chunk 会毁掉检索（原理）

这是面试最可能追问的点，必须能讲出来。

**Embedding 是把整段文字压缩成一个向量的"语义摘要"。** 当一个 chunk 里
混着"目录：第一章系统概述……第五章项目管理……"这种导航文本时：

1. 它的向量代表的是"一堆章节名的混合语义"，和任何具体问题都不够近；
2. 它占了 top-k 的位置（尤其是 top_k=1 时），把真正该命中的 chunk 挤掉；
3. 如果它混进正文 chunk（页脚"项目日志管理系统·产品手册 — 23 —"
   拼在正文末尾），会**稀释正文语义**，让这个 chunk 的向量偏离主题。

实测案例："忘记写日报怎么办？"曾经命中的是只含页脚的垃圾 chunk——
不是 embedding 模型不行，是我们喂给它的数据是脏的。

> **一句话（面试可用）：RAG 的检索质量上限在入库时就决定了，
> 数据清洗是成本最低、收益最大的优化。**

## 2. 改动一：噪声清洗（document_service.py）

### 2.1 噪声是怎么找出来的

不要凭感觉写过滤规则。先跑统计，让数据告诉你噪声长什么样：

```python
from collections import Counter
counter = Counter(line.strip() for line in lines if line.strip())
# 输出：'项目日志管理系统·产品手册' 出现 23 次（= PDF 页数）→ 页眉
# '— 23 —' 匹配正则 ^[—–-]\s*\d+\s*[—–-]$ 共 23 行 → 页码
# 29 行含 4 个以上连续点号 → 目录行
```

### 2.2 四条过滤规则

```python
PAGE_NUMBER_PATTERN = re.compile(r"^[—–-]\s*\d+\s*[—–-]$")   # 页码
TOC_DOT_PATTERN     = re.compile(r"\.{4,}")                   # 目录行（连续点号）
DROP_EXACT_LINES    = {"目录"}                                 # 孤立目录标题
# 页眉：出现 >= 8 次且长度 >= 6 的行自动识别
```

**为什么页眉用"出现次数"自动识别而不是写死字符串？**
写死 `"项目日志管理系统·产品手册"` 意味着换一个 PDF 就失效了。
用「出现次数 ≈ 页数」这个统计特征，任何 PDF 的页眉都能被抓住。

**为什么要求长度 >= 6？**
统计发现"字段""说明""操作"这些表格列头也重复出现 10 次左右，
但它们是正文内容。页眉是完整长标题，靠长度就能区分开。
这是"规则误伤"的典型案例——写过滤规则时永远要想：**会不会把正文也删了？**

### 2.3 清洗函数的位置（架构决策）

```python
def extract_text_from_pdf(file_path, clean=True) -> str
```

清洗放在**提取之后、切分之前**，并且保留 `clean=False` 参数返回原始文本。
为什么留这个开关：调试时需要对比"清洗前后"来确认过滤规则没有误伤正文
（`ingest.py` 每次入库都会打印"清洗前 X 字符 → 清洗后 Y 字符"）。

本次实测：10450 → 5627 字符，去掉了 46% 的噪声。

## 3. 改动二：章标题合并（chunk 切分）

dry-run 预览时发现新问题：chunk 0 只有"第一章系统概述"7 个字。
原因是第一章标题后面紧跟 1.1 小节，章标题被切成了独立废块。

**修法：章标题（第X章）不单独成块，作为前缀拼到下面第一个小节上。**

```python
if CHAPTER_PATTERN.match(line):        # 第X章 → 记下来，不开新块
    chapter_prefix = line
elif is_section_title(line):           # X.Y → 新块开头 = 章标题 + 节标题
    current_title = chapter_prefix + "\n" + line
```

**为什么要这么做（语义原因）：**
1. 7 个字的 chunk 向量没有信息量，还会占 top-k 名额；
2. "第一章系统概述
1.1 系统简介
……"这样的 chunk，标题本身就是强语义信号——
问"系统是什么"时这个 chunk 更容易被召回；
3. 面试讲法："我在切分时保证每个 chunk 自带章节上下文标题，
   相当于免费给 embedding 加了语义锚点。"

注意 `chapter_prefix` 用完要清空（`chapter_prefix = ""`），
否则会把同一个章标题拼给本章所有小节——这是这类状态变量最常见的 bug。

## 4. 改动三：入库脚本 + id 设计（vector_service.py / ingest.py）

### 4.1 为什么必须有 ingest.py

之前的问题根源：**改了切分代码但没有重新入库**，库里还是旧数据的 18 个 chunk。
没有入库脚本 → 每次改规则都要手搓命令 → 忘跑 → 代码和数据不一致。

现在 `python ingest.py` 一条命令完成全流程，还带 `--dry-run` 预览模式：
先看切分结果再入库，把"改规则 → 看效果 → 入库"变成可重复的安全流程。

### 4.2 id 从 chunk_{i} 改成 {文档名}_chunk_{i}

Chroma 的 id 全局唯一，重复 add 会报错。旧设计 `chunk_0, chunk_1...`
在入库第二个文档时必然 id 冲突。加上文档名前缀后多文档永不冲突。

### 4.3 metadata 加了 section 字段

每个 chunk 现在带 `section`（所属章节）。价值：
1. 自检和日志里能直接看出命中了哪一节（不用读 chunk 全文）；
2. 为下一课「引用精确到章节」铺路；
3. 以后做多文档过滤（按 source 查、按章节删）都靠 metadata。

### 4.4 reset_collection：为什么是删库而不是增量更新

清洗规则变了 = 旧数据全部不符合新规则。这时"增量更新"是错误思路，
正确操作是**清库重灌**。ingest.py 里 `reset_collection()` 先删再建。
（企业里会用 upsert + 版本号做增量，那是后面的课题，现在不需要。）

## 5. 改动四：阈值从 0.75 到 1.0（数据标定）——本课最重要

### 5.1 问题现场

数据洗干净后，"系统有哪些角色？"还是 MISS。排查发现：
检索其实**召回**了正确 chunk（6.3 角色权限，top-1），但距离 0.918
超过了阈值 0.75，被**过滤**掉了。

→ 结论：这次不是召回问题，是阈值问题。**两个问题的修法完全不同**，
排查时要先分清是哪一层坏了（这是 Debug 能力的核心）。

### 5.2 标定方法（背下来，面试必问"阈值怎么定的"）

用两组问题测 top-1 距离分布：

| 组 | 距离范围 |
|---|---|
| 10 个知识库内问题 | 0.548 ~ 0.918 |
| 5 个知识库外问题 | 1.155 ~ 1.306 |

两条分布之间有 0.92~1.16 的**隔离带**，阈值取隔离带中间：**1.0**。
- 太低（如 0.75）→ 库内问题被误杀（本次事故）
- 太高（如 1.3）→ 库外问题漏进来 → 触发幻觉

### 5.3 两个必须知道的坑

1. **距离的含义取决于度量和模型**：Chroma 默认用 L2（欧氏距离），
   不是余弦相似度。L2 的数值范围随 embedding 模型变化，**换模型必须重新标定**。
2. 阈值代码里写清标定日期和方法（见 rag_service.py 注释），
   三个月后的自己（和面试官）才看得懂 1.0 从哪来。

## 6. 验证方法（以后每次动数据都要走一遍）

```bash
cd 04_RAG_KnowledgeBase/backend

# 1. 预览切分质量（不写库）
python ingest.py --dry-run

# 2. 正式入库 + 内置自检
python ingest.py

# 3. 批量验证库内问题命中率（自己维护一份问题清单）
# 4. 验证库外问题仍被拦截（幻觉防护没被放宽的阈值破坏）
```

**自查清单（背下来）：**

- [ ] 库存量和切分数量一致（本次 28 = 28）
- [ ] 库内问题命中率 100%（本次 8/8）
- [ ] 命中的章节是"正确的章节"，不是碰巧相关
- [ ] 库外问题 0 引用、回答兜底话术（本次 2/2 拦截）
- [ ] 清洗比例合理（本次 46%，如果 >60% 要怀疑规则误伤正文）
