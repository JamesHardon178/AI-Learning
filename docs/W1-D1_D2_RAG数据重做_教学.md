## 1. 为什么垃圾 chunk 会毁掉检索（原理）

这是面试最可能追问的点，必须能讲出来。

**Embedding 是把整段文字压缩成一个向量的"语义摘要"。** 当一个 chunk 里
混着"目录：第一章系统概述……第五章项目管理……"这种导航文本时：

1. 它的向量代表的是"一堆章节名的混合语义"，和任何具体问题都不够近；
2. 它占了 top-k 的位置（尤其是 top_k=1 时），把真正该命中的 chunk 挤掉；
3. 如果它混进正文 chunk（页脚"项目日志管理系统·产品手册 — 23 —"
   拼在正文末尾），会**稀释正文语义**，让这个 chunk 的向量偏离主题。

实测案例："忘记写日报怎么办？"曾经命中的是只含页脚的垃圾 chunk——
不是 embedding 模型不行，是我们喂给它的数据是脏的。

> **一句话（面试可用）：RAG 的检索质量上限在入库时就决定了，
> 数据清洗是成本最低、收益最大的优化。**

## 2. 改动一：噪声清洗（document_service.py）

### 2.1 噪声是怎么找出来的

不要凭感觉写过滤规则。先跑统计，让数据告诉你噪声长什么样：

```python
from collections import Counter
counter = Counter(line.strip() for line in lines if line.strip())
# 输出：'项目日志管理系统·产品手册' 出现 23 次（= PDF 页数）→ 页眉
# '— 23 —' 匹配正则 ^[—–-]\s*\d+\s*[—–-]$ 共 23 行 → 页码
# 29 行含 4 个以上连续点号 → 目录行
```

### 2.2 四条过滤规则

```python
PAGE_NUMBER_PATTERN = re.compile(r"^[—–-]\s*\d+\s*[—–-]$")   # 页码
TOC_DOT_PATTERN     = re.compile(r"\.{4,}")                   # 目录行（连续点号）
DROP_EXACT_LINES    = {"目录"}                                 # 孤立目录标题
# 页眉：出现 >= 8 次且长度 >= 6 的行自动识别
```

**为什么页眉用"出现次数"自动识别而不是写死字符串？**
写死 `"项目日志管理系统·产品手册"` 意味着换一个 PDF 就失效了。
用「出现次数 ≈ 页数」这个统计特征，任何 PDF 的页眉都能被抓住。

**为什么要求长度 >= 6？**
统计发现"字段""说明""操作"这些表格列头也重复出现 10 次左右，
但它们是正文内容。页眉是完整长标题，靠长度就能区分开。
这是"规则误伤"的典型案例——写过滤规则时永远要想：**会不会把正文也删了？**

### 2.3 清洗函数的位置（架构决策）

```python
def extract_text_from_pdf(file_path, clean=True) -> str
```

清洗放在**提取之后、切分之前**，并且保留 `clean=False` 参数返回原始文本。
为什么留这个开关：调试时需要对比"清洗前后"来确认过滤规则没有误伤正文
（`ingest.py` 每次入库都会打印"清洗前 X 字符 → 清洗后 Y 字符"）。

本次实测：10450 → 5627 字符，去掉了 46% 的噪声。

## 3. 改动二：章标题合并（chunk 切分）

dry-run 预览时发现新问题：chunk 0 只有"第一章系统概述"7 个字。
原因是第一章标题后面紧跟 1.1 小节，章标题被切成了独立废块。

**修法：章标题（第X章）不单独成块，作为前缀拼到下面第一个小节上。**

```python
if CHAPTER_PATTERN.match(line):        # 第X章 → 记下来，不开新块
    chapter_prefix = line
elif is_section_title(line):           # X.Y → 新块开头 = 章标题 + 节标题
    current_title = chapter_prefix + "\n" + line
```

**为什么要这么做（语义原因）：**
1. 7 个字的 chunk 向量没有信息量，还会占 top-k 名额；
2. "第一章系统概述
1.1 系统简介
……"这样的 chunk，标题本身就是强语义信号——
问"系统是什么"时这个 chunk 更容易被召回；
3. 面试讲法："我在切分时保证每个 chunk 自带章节上下文标题，
   相当于免费给 embedding 加了语义锚点。"

注意 `chapter_prefix` 用完要清空（`chapter_prefix = ""`），
否则会把同一个章标题拼给本章所有小节——这是这类状态变量最常见的 bug。

## 4. 改动三：入库脚本 + id 设计（vector_service.py / ingest.py）

### 4.1 为什么必须有 ingest.py

之前的问题根源：**改了切分代码但没有重新入库**，库里还是旧数据的 18 个 chunk。
没有入库脚本 → 每次改规则都要手搓命令 → 忘跑 → 代码和数据不一致。

现在 `python ingest.py` 一条命令完成全流程，还带 `--dry-run` 预览模式：
先看切分结果再入库，把"改规则 → 看效果 → 入库"变成可重复的安全流程。

### 4.2 id 从 chunk_{i} 改成 {文档名}_chunk_{i}

Chroma 的 id 全局唯一，重复 add 会报错。旧设计 `chunk_0, chunk_1...`
在入库第二个文档时必然 id 冲突。加上文档名前缀后多文档永不冲突。

### 4.3 metadata 加了 section 字段

每个 chunk 现在带 `section`（所属章节）。价值：
1. 自检和日志里能直接看出命中了哪一节（不用读 chunk 全文）；
2. 为下一课「引用精确到章节」铺路；
3. 以后做多文档过滤（按 source 查、按章节删）都靠 metadata。

### 4.4 reset_collection：为什么是删库而不是增量更新

清洗规则变了 = 旧数据全部不符合新规则。这时"增量更新"是错误思路，
正确操作是**清库重灌**。ingest.py 里 `reset_collection()` 先删再建。
（企业里会用 upsert + 版本号做增量，那是后面的课题，现在不需要。）

## 5. 改动四：阈值从 0.75 到 1.0（数据标定）——本课最重要

### 5.1 问题现场

数据洗干净后，"系统有哪些角色？"还是 MISS。排查发现：
检索其实**召回**了正确 chunk（6.3 角色权限，top-1），但距离 0.918
超过了阈值 0.75，被**过滤**掉了。

→ 结论：这次不是召回问题，是阈值问题。**两个问题的修法完全不同**，
排查时要先分清是哪一层坏了（这是 Debug 能力的核心）。

### 5.2 标定方法（背下来，面试必问"阈值怎么定的"）

用两组问题测 top-1 距离分布：

| 组 | 距离范围 |
|---|---|
| 10 个知识库内问题 | 0.548 ~ 0.918 |
| 5 个知识库外问题 | 1.155 ~ 1.306 |

两条分布之间有 0.92~1.16 的**隔离带**，阈值取隔离带中间：**1.0**。
- 太低（如 0.75）→ 库内问题被误杀（本次事故）
- 太高（如 1.3）→ 库外问题漏进来 → 触发幻觉

### 5.3 两个必须知道的坑

1. **距离的含义取决于度量和模型**：Chroma 默认用 L2（欧氏距离），
   不是余弦相似度。L2 的数值范围随 embedding 模型变化，**换模型必须重新标定**。
2. 阈值代码里写清标定日期和方法（见 rag_service.py 注释），
   三个月后的自己（和面试官）才看得懂 1.0 从哪来。

`rag_service.py` 中：
```python
TOP_K = 3   # 原来写死 top_k=1
result = search(query_embedding=query_embedding, top_k=TOP_K)
```

改造后实测：

| 场景 | top_k=1（改前） | top_k=3（改后） |
|---|---|---|
| 忘记写日报怎么办？ | 只命中 3.1，缺 FAQ 补录信息 | 命中 3.1 + **第七章常见问题** + 第三章，答案完整 |
| 系统有哪些角色？ | 曾 MISS | 命中 6.3 + 1.2 |
| 8 个库内问题命中率 | 6/8 | **8/8** |
| 库外问题幻觉防护 | 有效 | 仍然有效（0 引用） |

### 8.2 作业思考题的答案（面试必考）

**① 阈值过滤后剩 0 个 chunk，兜底还成立吗？**

成立。`retrieve_documents` 返回空列表 → `build_context` 拼出空 context →
`build_prompt` 里【知识库内容】为空 → prompt 规则第 3 条要求
"如果知识库没有相关信息，只回答：知识库中没有找到相关信息。"
实测"量子计算机原理""写诗"均返回兜底话术、0 引用。

**② 3 个 chunk 全给 LLM 会不会被干扰？**

会，这就是 **precision vs recall 的 trade-off**：
- top_k 越大 → recall（召回）越高，但噪声越多，LLM 可能被不相关内容干扰；
- top_k 越小 → precision（精确）越高，但容易漏掉真正相关的（如 FAQ 场景）。

**正确做法不是二选一，而是"大 top_k + 阈值过滤"**：
先召回 3~5 个候选（保证 recall），再用距离阈值过滤掉不相关的
（保证 precision），只把"相关的"喂给 LLM。
这就是 `TOP_K=3 + DISTANCE_THRESHOLD=0.95` 的组合逻辑——
top_k 管"召回多少候选"，阈值管"放行哪些"。

**③ 那为什么答案还是只有 3 个引用？**

因为 `build_citations` 基于**过滤后**的 metadatas 生成，
只有通过阈值的 chunk 才会进 context 和 citations。
这就是"召回 3 个 → 过滤 → 只留相关的"完整链路。

改完跑第 6 节的自查清单验证（本次 8/8 通过）。

## 9. D3 文档上传接口（2026-09-01 完成）——踩了 3 个坑

D3 目标：新增「文档上传 / 列表 / 删除」接口，让知识库可自助扩展。
本次共改 3 个文件 + 新增 1 个：`main.py`、`document_registry_service.py`（新增）、
`document_service.py`、`requirements.txt`。

### 9.1 坑 1：装饰器空挂 = 路由被"吃掉"（最隐蔽的 bug）

**现场**：`/api/rag/query` 返回 400，报 `missing file` 字段错误——
明明是 query 接口，却在要上传文件。

**原因**（看 main.py 原始代码）：
```python
@app.post("/api/rag/query", response_model=RAGQueryResponse)   # ← 装饰器下面没有函数！
@app.post("/api/rag/documents/upload")                          # ← 下一个装饰器
async def upload_document(file: UploadFile = File(...)):        # ← 被上面两个都装饰了
```

Python 装饰器是"从下往上"应用的：`upload_document` 先被
`/documents/upload` 装饰，**又被 `/api/rag/query` 装饰** →
一个函数注册到两个路由，query 路由被 upload 函数接管。

**教训**：装饰器必须紧贴函数定义。中间任何空行/注释都会导致
"装饰器漂移"。这是面试可以讲的 Debug 案例——
从"接口报错"倒推"装饰器绑定错了函数"。

**修法**：query 装饰器移回 `rag_query_api` 上方，函数体紧跟。

### 9.2 坑 2：注册表 JSON 结构不一致

**现场**：`GET /api/rag/documents` 返回双重嵌套
`{"documents": {"documents": [...]}}`；删除文档时遍历 dict 直接崩溃。

**原因**：注册表文件结构是 `{"documents": [...]}`（dict 包 list），
但 `get_documents()` 返回整个 dict，main.py 又包了一层 `{"documents": ...}`。

**修法**：统一"读 → 返回 list"的契约：
```python
def get_documents() -> list[dict]:
    """返回文档列表（不是整个 dict）"""
    return _load_registry()   # 内部从 {"documents": [...]} 里取 list
```
**教训**：文件存储结构 ≠ API 返回结构 ≠ 函数返回值。
三层各自定义清楚，用"返回 list"作为统一契约。

### 9.3 坑 3：页眉检测误伤"重复正文"（回归引入 + 当场修复）

**现场**：测试上传一个内容重复的 PDF，清洗后 6674 → 71 字符，
几乎全部被删。原因是页眉检测规则是"出现 >= 8 次即页眉"，
而重复正文每页出现 30 次，被误判成页眉。

**修法**：页眉的特征不是"出现次数多"，而是"出现次数 ≈ 页数"。
给 `detect_page_headers` 加 `page_count` 参数和**上下限**：
```python
lower_bound = min(min_count, max(3, page_count))   # 太少不是页眉
upper_bound = page_count * 1.5                     # 太多是重复正文，不是页眉
```
**回归验证**：产品手册仍 5627 字符 / 28 chunks（页眉照删）；
重复正文 PDF 保留 6599 字符（不再误伤）。

**教训**：写过滤规则一定要想"会不会误伤正文"。
判据要选**能区分噪声和正文的特征**（页眉=每页1次），
而不是"看起来重复"这种模糊直觉。

### 9.4 上传接口的防御（扫描版 PDF 拦截）

发现用户上传的《计算机网络》PDF 是"读秀"扫描版：正文全是图片，
只有目录页有文字。提取 3798 字符切出 208 个 chunk，全是孤立标题行。
**这种文档入库只会制造垃圾向量。**

`main.py` 上传接口加了 3 道防御：
1. 文件类型校验（非 .pdf → 400）
2. 重复上传校验（已存在 → 409）
3. **文本量校验**：提取文本 < 2000 字符 → 422 拒绝
   （扫描版/坏 PDF 的典型特征就是文本量极少）
